# Plan › Pantry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** add Plan › Pantry to the React PWA, covering:

- the stock list with ± buttons;
- add, search and barcode scan;
- the product detail page;
- the shopping list, with ticks, one-off lines and "Add to pantry";
- a prompt after saving an expense;
- a Home row.

The server side adds the `shopping_lines` table and the stock endpoints the PWA is missing.

**Architecture:** three parallel streams, each in its own worktree cut from `p5/pantry`:

| Stream | Branch | Worktree | Covers |
|---|---|---|---|
| B (server) | `p5/pantry-b` | `~/expenses-p5-b` | the server work |
| Wa (web) | `p5/pantry-wa` | `~/expenses-p5-wa` | the list, add/scan and detail |
| Wb (web) | `p5/pantry-wb` | `~/expenses-p5-wb` | the shopping list, the post-save prompt, the Home row and the notification links |

Both web streams write types by hand from spec §3, in their own files. The integration step merges B, then Wa, then Wb. It then runs `gen:api` and switches the hand-written types to aliases of the generated schema.

**Tech Stack:** FastAPI, SQLAlchemy, Alembic and Pydantic v2, tested with pytest on SQLite plus Postgres `t_pantry`. React 19 with `useCachedQuery`, `useAction` (queued), `useOnlineAction` and Vitest.

**Spec:** `docs/superpowers/specs/2026-10-08-pantry-design.md` is binding. § references below point to it.

## Global Constraints

- One migration only, `e1f2a3b4c5d6`, which revises `d0e1f2a3b4c5`. There must be a single alembic head.
- The existing `/stock`, `/stock/shopping`, `/products/*` JSON keys and value types stay unchanged. Only additions are allowed, and snapshot tests pin the old shape first.
- No Pantry code path creates, changes or deletes a Transaction.
- Online-only writes: add product, settings, refresh, archive and apply-ticked. Queued writes: stock adjust (with `client_id`), ticks and one-off lines.
- Additions to `data/keys.ts` must not rename anything.
  - Wa owns `stockList` and `stockItem(id)`.
  - Wb owns `shopping` and `stockSummary`.
- The barcode scanner module is loaded with a dynamic import and never ends up in the main chunk. No CSP change unless it is unavoidable; if one is unavoidable, stop and report it instead.
- Layout at 390×844 must have no horizontal overflow and use 44 px targets. `.ui-num` inside running text must wrap.
- Do not modify or weaken existing test cases. Adding new ones is fine.
- Commit by explicit path. Do not push, and do not spawn subagents.

## Review Focus

1. A queued + tap replayed twice (a lost reply, then a retry) must add once. That is the `client_id` dedupe.
2. apply-ticked is called while another member unticks or archives at the same time. It must run in one transaction, with no adjust on an archived item, and a second call must return empty.
3. Two people tick the same item. The partial unique index means one active tick, and the API must stay idempotent.
4. The camera is denied, or the browser is iOS Safari without the API. The typed-barcode fallback must be focused and must work.
5. The post-save prompt must never delay or break the composer save, including when offline or when the summary call fails.

### Task B2: `shopping_lines`, ticks, one-off lines, apply-ticked and the shopping extensions

**Files:**

- Tests: `tests/test_shopping_lines.py` (new), `tests/test_migrations.py` and `tests/test_planning_upgrade.py` (add new cases only)

**Interfaces (produced):**
- `tick_item(db, hh, user, stock_item_id, quantity=None) -> ShoppingLine` (idempotent)
- `untick(db, hh, tick_id)`
- `add_line(db, hh, user, name, quantity=None)`
- `set_line_checked(db, hh, line_id, checked)`
- `delete_line(db, hh, line_id)`
- `apply_ticked(db, hh, user) -> {"applied": [...], "cleared_lines": int}`
- `active_ticks(db, hh) -> dict[stock_item_id, ShoppingLine]`

- [ ] **Step 1.** Write failing tests. Each item below is its own test:
  - Migration: upgrade and downgrade round trip; the partial unique index rejects a second active tick on SQLite and on Postgres.
  - Ticks: idempotent; foreign or archived item → 404; untick.
  - One-off lines: create, check, uncheck, delete; an empty name → 422.
  - apply-ticked:
    - stock goes from 0 to 2 for a tick with quantity 2, and the response has `before` and `after`;
    - checked lines are cleared and unchecked lines stay;
    - an item archived after it was ticked is cleared without an adjust;
    - a second call → `applied` is empty;
    - **the Transaction count is unchanged**.
  - Archive clears the active tick.
  - `GET /stock/shopping` items have `name, unit, need_qty, ticked, tick_id`; the response has `unpriced, lines, ticked_count`.
  - `GET /stock` has `ticked` and `tick_id`; `/stock/summary` has `ticked_count`.
  - Household isolation on every new route.
- [ ] **Step 2.** Run the tests and confirm they fail.
- [ ] **Step 3.** Implement it as spec §3.1–§3.2 describe. apply-ticked runs in a single DB transaction.
- [ ] **Step 4.** Run the new and existing stock tests, migrations and upgrade tests. Run the Postgres set on `t_pantry`.
- [ ] **Step 5.** Commit: `feat(stock): shopping_lines (ticks, one-off lines), apply-ticked`.

First check whether the composer's `client_id` mechanism is generic and reuse it. Otherwise add the smallest store that works. If that needs a column, put it in `shopping_lines`' migration file only if it is still unmerged; otherwise write a ruling in the report and use an existing table.
